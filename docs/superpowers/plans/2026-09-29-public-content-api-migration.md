# 用户端接入真实 API

## 目标

文章、独立页面和足迹从后端公开 API 读取；发布或更新内容后，用户端无需重新构建。首页、列表、详情、分类、标签、系列、搜索、RSS 和 sitemap 都使用同一份后端数据，不再读取本地 `.md` 或 `config/footprints.yaml`。

## 图片怎么处理

| 图片 | 本期做法 |
| --- | --- |
| 新增内容图片 | 管理前端调用 `POST /api/v1/admin/media` 上传，保存返回的媒体 ID 或 URL；公开前端使用后端提供的 URL，不拼 `/uploads/{文件名}` |
| 文章封面 | 旧封面沿用现有导入器；新封面上传后保存 `coverMediaId`。后端公开文章响应补 `coverUrl`，列表和详情直接使用 |
| 足迹图片、头像、默认分享图、分类图、系列封面 | 上传后保存后端 URL，公开页面从足迹或站点内容接口读取 |
| 旧文章正文图片 | 暂不迁移，保留原 Markdown 引用；新正文图片继续用现有编辑器上传流程 |
| 站点头图及响应式图片 | 暂用本地文件；以后上传后修改 `Cover.astro` 的 URL |
| logo 等静态资源 | 继续放在前端 |

历史导入器只负责一次性迁移旧数据；日常新增图片走管理前端上传。后端现有 `sitecontent` 字段已能保存头像、分类图和系列封面的 URL，无需为它们新增字段。

## 实施顺序

1. **补接口：**后端为公开文章列表和详情增加 `coverUrl`，有封面时返回可加载的 URL。更新 Swagger，再运行 `pnpm api:update`。不得从 `coverMediaId` 猜文件名。
2. **迁旧数据：**预检查并备份后，使用现有导入器迁文章、独立页面、足迹和旧封面；核对数量、slug、语言和图片。站点内容图片由管理前端上传，再把返回的 URL 保存到现有字段。
3. **建公开 API 客户端：**服务端使用 `BACKEND_API_URL` 调用文章、页面、足迹和站点内容接口；统一处理超时、404 和后端错误。公开读取不使用管理员 Cookie 或 CSRF token。
4. **切页面：**给实际部署环境配置 Astro adapter，内容相关路由按请求渲染；复用现有 Markdown 渲染效果。首页、列表、详情、分类、标签、归档、系列和多语言路由改读 API；足迹和站点内容图片使用后端 URL。
5. **切搜索与 SEO：**搜索使用文章接口的 `q` 参数；RSS 和 sitemap 按请求生成。缺失文章返回 404，后端故障显示错误，不回退到本地 Markdown。
6. **清理与上线：**确认所有运行时本地内容读取已移除，再归档旧 `.md`、足迹 YAML 和无用生成脚本。保留旧正文图片、站点头图及静态资源；先部署后端与媒体，再部署前端。

## 必须核对

- 文章列表有分页，`limit` 最大 100；列表 `bodyMarkdown` 为空，详情需单独请求。分类、标签、归档等全站统计必须遍历完整分页结果。
- 后端分类是扁平数组，旧站的嵌套分类需从 `extra` 恢复或补明确字段；多语言回退和 canonical 保持现有规则。
- 实测发布、修改、撤回文章无需重建即可反映在页面、搜索、RSS 和 sitemap；检查 404、图片 URL 的 200 响应与 MIME、`pnpm api:check`、测试、`pnpm lint:fix`、`pnpm check`、`pnpm knip` 和 `pnpm build`。
- 部署目标尚未确定；选定 adapter 后在实际按请求运行环境验收，不能只用 `astro dev` 判断完成。
